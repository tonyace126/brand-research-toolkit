# Repo / 連結安裝評估

把一個外部 repo 或工具連結，跑一套「先稽核、後採用」的固定流程。**核心原則:評估階段全程唯讀，絕不安裝、絕不執行外部程式碼。** 過了關、且使用者點頭，才進實作與驗證。

## 觸發

使用者給一個連結 + 類似「能不能裝 / 評估看看 / 安不安全 / 該不該用」的字眼時。

## 流程(四步,依序)

### 1️⃣ 風險稽核(這是閘門,沒過就停)

實際讀原始碼(不是只看 README)。建議派 subagent 做 fan-out 逐檔掃描,逐項給**證據(檔案路徑 + 它做了什麼)**。七個面向:

| # | 面向 | 查什麼 |
|---|---|---|
| 1 | 資料外洩 | 是否連到文件記載 API **以外**的主機?列出**每一個**對外 host。標出像作者自家伺服器/analytics/不明收集點的東西。 |
| 2 | 遙測 / 回傳 | 安裝或執行時是否 ping home / 連 license / 啟用伺服器? |
| 3 | 隱藏付費 | 安裝/執行會不會綁定作者帳號、訂閱、分潤/推薦連結、註冊? |
| 4 | 金鑰處理 | 機密怎麼存(.env)?有沒有 log / print / 傳到不該傳的地方?`.env` 有 gitignore 嗎? |
| 5 | 安裝腳本 | `install.sh` 有沒有 `curl\|bash`、`sudo`、下載 binary、改 repo 外的系統檔? |
| 6 | 自動執行副作用 | hook/事件是否自動觸發**不可逆**動作?有沒有 dry-run 預設?新裝會不會直接亂發/亂寫? |
| 7 | 混淆 | 有沒有 `eval`/`exec` 遠端內容、base64 blob、minify、刻意藏行為的東西? |

**輸出**:七面向裁決表(✅ SAFE / ⚠️ CAUTION / 🔴 RISK),每項一句理由 + 證據檔案。

### 2️⃣ 架構建議

針對「東西越來越多怎麼組織」:
- **模組分開,不整併** —— 一個能力一個模組,任何一個壞掉不拖垮其他。
- **觸發分三層**:
  - 🟢 **自動觸發(hook)**:只放安全、可重複、可逆、不需確認的動作(例:完成→發通知)
  - 🟡 **關鍵詞/指令**:任何寫外部、會花錢、有後果的動作
  - 🔴 **手動+二次確認**:不可逆 / 大量 / 對客戶的動作
- **鐵律**:絕不把「發信、改 CRM、花 API credit」放進自動觸發層。

### 3️⃣ 資源評估(找出沒寫在 README 的坑)

- **token**:hook 跑 Python handler ≈ 0 token;真正會爆的是「把 LLM/subagent 綁到高頻事件」(如 `PostToolUse *`)。
- **資源/記憶體**:短命 subprocess 通常很輕;注意高頻事件狂 spawn + 撞 API rate limit / 燒 credit。
- **維護腐化**:每個外部整合 = 一個會隨對方 API 改版而壞的點。整合越多,維護負擔越重 → 只採用真的會用的。
- **其他常見坑**:`settings.json` 合併衝突、金鑰擴散、user 層 vs 專案層 scope(全域會污染所有專案)、重複觸發(idempotency)、靜默失敗(hook 掛了不自知)。

### 4️⃣ 建議 + 最小安全原型

- 明確建議:整套採用 / 只取 1–2 塊 / 不採用。
- 若採用,**先做最小、最安全的一塊**驗證價值:
  - 安全預設(預設 dry-run,要明確開關才真發)
  - 專案層 scope,不污染其他專案
  - 只接一個整合、低頻事件
  - 金鑰走 `.env`(gitignore),不寫死

## 收尾

過關且使用者同意後,才進「實作 → 驗證」。驗證盡量用真實通道跑一遍,確認端到端通了再收工。
